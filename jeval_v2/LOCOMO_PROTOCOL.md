# Headline experiment: cosine versus EPE as input to the same LLM

## Question

On LoCoMo, does giving the **same answer model** an EPE-based compression-risk score lead to better answers than giving it a cosine-based compression-risk score, when question, compressed memory, prompt, and decoding are otherwise identical?

The answer model does not see the original source. A risk score does not contain the omitted fact, so this experiment can test better uncertainty/abstention and answer choices from available memory. It cannot establish that the score repairs missing evidence, retrieval, or a memory store.

## Fixed setup before observing answers

1. Pin the official [LoCoMo `locomo10.json`](https://github.com/snap-research/locomo/blob/main/data/locomo10.json) revision and question IDs. All QA questions are in scope unless exclusions are written down before running. The ten conversations are the source groups; do not treat thousands of questions as independent histories.
2. Pin a single compression pipeline and target budget. For every question, choose the **same compressed memory text** for both arms. If retrieval selects multiple compressed units, freeze selection and order before scores are attached; EPE/cosine may **not** select different units. Document how unit scores are reduced to one question score (a prespecified maximum, for example). No original source or official answer belongs in the answer prompt.
3. Pin one encoder and revision, one EPE predictor checkpoint trained on non-LoCoMo original–compression pairs, and one answer model/version with fixed decoding settings. Model identity, prompt, and system instruction must match across arms. Use a fresh independent model call for each prompt; do not put A and B in one context.
4. Normalize cosine and EPE independently to within-run midrank percentiles, higher meaning more apparent information loss. This gives identical units without using answer labels. The only changed prompt field is the percentile. Raw score and percentile remain in the separate key. A percentiled score cannot reveal a deleted event such as “fired.”

## Input to the prompt renderer

Make a JSONL with one row per LoCoMo question. The score refers to **the exact compressed memory in that row**:

```json
{"id":"conversation_id:0","question":"Does Maya currently work there?","answer":"No","compressed_memory":"Maya was hired in January.","cosine":0.12,"epe":0.31}
```

The `answer` is optional for prompt rendering but useful in the blinded review sheet. It never enters the LLM prompt. This score-joined file is **not yet generated by the repository**: the benchmark adapter provides question/evidence metadata, while compressor, memory selection, and score-to-question joining still need implementation and a frozen specification. Do not substitute synthetic demonstration rows for benchmark measurements.

Render the two parallel prompts:

```bash
python -m jeval_v2.locomo_prompt_pairs --input outputs/locomo_scored_questions.jsonl --output-prefix outputs/locomo_pair --seed 0
```

Outputs:

- `locomo_pair.prompts.jsonl`: two prompts per question, labeled A/B, with no arm name or reference answer.
- `locomo_pair.key.jsonl`: arm mapping and raw/percentile scores. Keep hidden until review is complete.
- `locomo_pair.review.jsonl`: blank A/B answers, correctness, support, and notes for manual judging.

Check that both prompts for an ID have identical memory and question and differ only in the displayed risk number. If both percentiles tie, prompts are identical; keep those cases and report them.

## Answer collection and manual review

Run each prompt through the same model in a fresh context. Fix temperature (prefer 0), model version, system message, max output tokens, and tool access. Save raw request and response with ID/side and token usage. The repository currently **renders prompts but does not call an LLM**; no model/provider has been selected.

For each question, paste A/B answers into the review sheet and compare against LoCoMo's reference answer and evidence dialogue IDs. Judge both arms while the mapping key is hidden:

- `correct`: does the answer resolve the official question correctly? Record ambiguous references in notes.
- `supported`: does the shown compressed memory support the answer? A correct guess unsupported by the memory should not count as an evidence-supported success.
- `abstained`: record “do not know” separately from a wrong assertion (add to notes or analysis sheet).

Predefine the rubric on a small *non-LoCoMo* development set, then review all LoCoMo cases once. Keep the judgment file and raw answers. Reveal the key only after review; have a second reviewer check disagreements or a prespecified sample if feasible.

## Analysis and interpretation

Primary paired table: both correct, EPE only correct, cosine only correct, neither. Repeat for evidence-supported correctness, abstention, and each LoCoMo QA category; show results by the ten source conversations and avoid overstating precision. Report the number of tied risk prompts. The two arms should have the same context-token count apart from the numeric field and identical answer-model settings; report any actual token differences and cost.

An EPE advantage means the LLM made better use of **this displayed risk signal under this prompt**. It does not show EPE can retrieve a missing fired event. If both arms answer wrongly from “hired” alone, report the failure. If the cosine and EPE rankings are nearly identical, a null result is expected. Do not change prompts, thresholds, compressor, or score aggregation after seeing test answers.
